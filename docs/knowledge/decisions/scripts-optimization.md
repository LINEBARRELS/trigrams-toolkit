# 脚本基础能力与 CI 验收取舍

决策日期：2026 年 10 月 29 日。

## 背景与依据

用户要求基于 `scripts/` 静态审计制定完整优化计划，同时解决优先问题和可选精简。现有部署契约规定候选验证、版本切换、归属保护、锁与回退；审计发现重复的底层实现、手工依赖闭包和 CI 编排问题。没有取得真实 CI 失败日志，历史故障原因仍待运行证据核对。

## 选择

- 保留既有归属保护、共享/独占锁和单份 previous 回退；底层锁暂沿用当前实现。Portalocker 的 Windows 共享锁需要额外的 pywin32，本轮缺少引入成本优于现有实现的证据，不为替换锁而扩大运行依赖。
- 原子文件发布和严格 JSON 处理复用公共维护源。Schema 文档与运行时值若有不同输入约束，应明确边界；不以复用为名悄然加严格式。
- Python 依赖构造交给已有安装工具，以 requirements 为入口，删除脚本手工维护的传递依赖闭包。显式准备依赖材料，部署消费本地材料；源包和发布包路径都保留隔离与无网络部署能力。材料位置、准备入口和版本约束由框架 Task 在实际维护源确定。
- 新版本提交完成后，历史清理失败作为成功结果中的结构化未完成清理信息返回，退出码保持成功；提交前发布失败继续回退并返回失败。持久部署记录与本次操作结果分别维护。
- 完整业务流程按平台验收一次；其他 shell 保留入口与协议检查。源码业务回归继续覆盖规则，真实包验收继续覆盖材料完整性和部署行为。
- 全部 5 项可选精简纳入实现与验收；不为此增加通用事务框架、全量文件摘要校验或新的包管理器。

## 影响与承接

操作结果、依赖材料及 CI 责任分配的原实施 Plan（`scripts-optimization`）已随旧仓归档；现行校验与维护入口以 [维护与发布说明](../../maintenance.md) 及各工具帮助与协议为准。

本轮计划不包含真实用户目录部署或版本发布。历史 Plan 与审计证据保留原记录；调用方继续使用现有基础校验入口和 JSON 成功语义。
