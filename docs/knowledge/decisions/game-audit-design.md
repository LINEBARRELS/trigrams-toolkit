# game 改造的核心设计决策

记录日期：2026 年 10 月 26 日。

本记录保存 game 扩展改造采用的方向及取舍理由。

## 1. game 只保留领域增量

通用规划、执行、审核、身份定位与安装复用 core，game 提供玩法和视觉行为、专业方法与判断标准。这样可集中维护通用协议，同时让领域交接承载实际的游戏开发需求。

## 2. 用 Spec 网络组织玩法，取消独立 GDD

每份 gameplay-spec 描述自身边界内的完整运作，主、子和桥梁只表示组合角色。领域由相关 Spec 组织，新增跨领域互动由桥梁 Spec 承载；产品阶段目标归 PRODUCT。

这使设计能按内聚玩法逐步发展，减少总览文稿与局部规则的重复。相应代价是组合约束和共享机制的变更影响需要显式核对。

## 3. 设计先收敛，正式 Spec 再进入实现规划

玩法探索直接用于讨论与研究，玩法开发形成确定规则和验收，之后才交给 to-plan 安排实现。两者可以共用格式，但研究稿不因此成为正式依据。

这样保留讨论的试探空间，避免把尚未确定的机制固化成执行要求。该条件约束 game 的玩法实现入口，不收窄 core 的其他规划用途。

## 4. 程序方法增量组合，引擎差异按需加载

游戏程序开发复用 core 编程方法，补充可运行场景、试玩、运行证据和整合验收；引擎操作先作为配套方法。只有出现独立工作与交接需求时，才拆出引擎 workbook。

运行截图、指标与复现信息是具体交付的证据，按验收选择。这样既能承接游戏开发特有的验证，也避免维护多套重复流程。

## 5. 方法、判断与资料分别维护

workbook 定义工作方法，principle 按实际读取目的拆分判断主题，格式与模板保持单点维护。外部文章和案例作为参考，提炼出有适用条件的判断后再进入专题 principle。

划分依据是消费者的问题与读取条件，而非一个总括目录。这样减少无条件加载和多份权威正文，也保留参考观点与项目规则的区别。

## 6. 玩法身份与技术归属分开

Spec 的稳定身份和组合关系复用 Project State，玩法可以先于技术 Module / Feature 独立登记。组合关系表达直接使用关系，玩法反馈循环写在 Spec 中。

这样允许设计按玩法演进，技术架构按实现职责演进，避免为登记方便把两种边界强行对应。

## 7. 先核验迁移与交接，再进入源码实施

现有 Plan 承接材料与消费者核对、场景演练和实施拆分，以本轮已选方向作为基线。审计补充事实和影响，演练验证方法能否交接，后续再实施源码改造。

这样既保留必要验证，也避免重新从空白讨论已经确定的方向，或在替代入口可用前清除旧能力。
