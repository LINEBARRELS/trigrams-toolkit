# workbook 执行方法与 Plan 编排调度的解耦

决策日期：2026 年 10 月 28 日。

## 目的与背景

检视既有工具包体系时发现，虽然底层规范（`to-plan` 与 `toolkit-steward` 架构说明）支持单步与轻量工作直接执行，但在维护原则（`structure-workbooks-for-plan-translation`）、workbook 标准章节组织及部分领域技能路由中，存在将 `workbook` 默认归宿假定为“必须被 `to-plan` 转化为 Task”的设计惯性。

用户指出：`workbook`（工作方法）与 `principles`（判断标准）构成灵活的认知资产层，许多具备确定输入与验收条件的工作，直接加载适用准则或规程即可开展实施。随着大语言模型理解、推理及长程自调度能力的持续提升，过度绑定 `to-plan` 会引入不必要的实体与管理摩擦。

## 核心选择

明确“认知资产层”与“编排脚手架层”的双层正交定位：

1. **职责分离**：
   - `principles` 与 `workbook` 属于领域认知资产，负责提供客观的判断标准与标准作业规程，独立于任务调度形式存在。
   - `to-plan`、`plan-toolkit` 与 `execute-plan` 属于面向复杂、多角色、异步交接或需机器审计追踪时的物理编排脚手架。
2. **解除单向从属绑定**：
   - `workbook` 的使用场景不限于向 `to-plan` 供给 Task 切分依据。它既可由 `to-plan` 编译为带 Stub 与依赖拓扑的正式 Plan，也可直接被具备足够能力的前沿模型直接加载并在单任务上下文中自调度执行。
3. **规范章节与指引表述**：
   - 维护原则将章节要求规范为“适用与输入、必要工作流程、工序切分与交接（或 Task 切分与交接）、产出与验收”。工序说明兼顾直接执行的步骤指引与规划拆分输入。
   - 领域技能（如 `game-designer`）对下游实现的路由，由硬编码交付 `to-plan` 软化为按任务规模灵活分流：多阶段复杂系统交付交给 `to-plan`，明确且集中的单步工作可直接依据 workbook 执行。

## 实施取舍

保持既有契约与历史证据严格向后兼容：

- 不破坏既有 `plan-toolkit` 门禁契约、Stub 两阶段验收、快照同步逻辑及历史 Plan 审计档案。
- 既有已入库的 `WORKBOOK.md` 中保留的 `## Task 切分与交接` 标题继续被规范包容，不进行无必要的破坏性全局重命名。
- 在 `toolkit-maintenance` 的 `structure-workbooks-for-plan-translation` 原则与领域技能路由中完成微调，建立双轨并行的设计依据。

## 承受的代价

- 直接依据 `workbook` 开展单任务或自主执行时，不产生 `plan.json` 机器状态与自动化锁，无法使用 `plan-toolkit mark` 进行工序级机器状态追踪。
- 该模式下的交付质量保障转为依赖执行者自律、规程自查与独立审核入口（`delivery-review`）。
- 实践中需要使用者与 Agent 建立合理的复杂度分流意识：高风险、跨角色交接、多异步模块的系统工程继续使用 Plan 组织；轻量、聚焦、上下文闭环的确定性工作优先轻装直行。

## 依据与承接

依据 2026 年 10 月 28 日对话中确立的宏观方向。本记录作为后续工具包演进、workbook 编写、原则入库与模型交互流程设计的设计指引。
