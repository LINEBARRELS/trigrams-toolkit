# Gameplay Spec 格式与填充规范

主、子与桥梁 Spec 共用本格式及[模板](../assets/templates/gameplay-spec.temp.md)。每份 Spec 描述自身边界内的完整运作，按实际设计取用章节。正式定稿登记身份；使用本结构整理候选方案时，研究草稿仍保持研究身份。

## 章节职责

| 章节 | 编写内容 |
| --- | --- |
| 目标与组合边界 | 玩家目标、目标体验、本 Spec 负责范围，以及直接组合的 Spec 身份、职责与新增互动 |
| 术语、实体与状态 | 本玩法新增的专有术语、实体、状态合法值域、操作标识、共享范围，以及跨步骤成立的状态约束与派生关系 |
| 核心内循环 | 3–5 步的 Mermaid 循环图与分步详解；按步骤归集触发输入、状态转移规则、失败与临界边界、决策反馈 |
| 验收标准 | 从自身规则推导的可判定核心结果、关键约束与失败边界 |

## 术语、实体与状态写法

新增专有概念使用稳定的英文标识，在表中标注 `Term`、`Entity`、`State` 或 `Operation`：

- **术语（`Term`）**：局部玩法概念在本 Spec 定义；跨玩法共享或上升为全局业务概念时上浮至 `PRODUCT.md`，并在本 Spec 注明来源。
- **实体（`Entity`）与状态（`State`）**：写明实体的玩法职责、状态合法值域（枚举、数值区间或结构）、适用对象（世界、区域、玩家或局部实体）及共享范围。核心内循环引用的状态均应在此声明或指明上游来源。
- **操作（`Operation`）**：按玩家意图命名；`press`、`hold`、`release`、`drag`、`repeat` 等输入语义在影响规则裁决时写明。
- **状态约束与不变式**：描述在适用范围内始终成立的状态关系、容量上限与派生值计算关系，分配 Spec 内唯一的 `R-xx`（两位数字）标识。单个状态的静态值域留在定义表中，不重复立为约束规则。

## 核心内循环与分步规则写法

核心内循环是 Spec 的结构主干。先用 Mermaid `flowchart` 绘制 3–5 步的完整回路，呈现从感知机会、玩家操作或自动演进、规则裁决、状态结算到反馈并塑造后续决策的流转路径及关键分支；单次运作可到达终态时一并标出。

流程图后按步骤编号逐节展开，将规则与反馈就地挂载到所属步骤，不拆分为孤立表格：

1. **触发与输入**：说明进入该步骤的玩家操作意图、输入语义或系统自动触发事件。
2. **规则与结算（`R-xx`）**：与状态约束共用 Spec 内唯一的 `R-xx` 编号。每条变化规则对应一次可独立判定的结算或阶段变化，写明前置条件、作用对象，以及同一次结算内的全部赋值、增减、生成、移除或关系变化。有独立触发、条件或中间状态时拆分为不同步骤或子阶段。
3. **失败与边界**：含条件判定的步骤写明条件不足或动作失败时的实际结果（保持原状态、消耗部分代价或转入惩罚分支），并聚焦影响裁决的阈值、上下限、初始化、重置、重复触发与结算顺序。
4. **互动反馈（`F-xx`）**：使用 Spec 内唯一的 `F-xx`（两位数字）标识，由对应步骤或规则引用，说明玩家可获知的信息内容、出现时机，以及影响决策或结算的持续时间、遮挡、优先级或结束条件。具体按键映射与 HUD 布局引用 `DESIGN.md`，画面、镜头与特效表现引用 `docs/GAME-VISUALS.md`。

## 组合、身份与验收

主、子和桥梁表示 Spec 在具体组合关系中的角色，而非固定机制分类；同一份 Spec 可组合较小机制并供上层玩法复用。直接组合关系仅列本 Spec 直接使用的下层机制，说明原职责与新增互动；`game:composes` 登记方向为 `组合 Spec -> 被使用 Spec`。正式 Spec 保留工具维护的 `artifact-id`，研究草稿以普通链接指向既有正式 Spec。

验收标准从本 Spec 拥有的确定规则推导，使用简短可判定断言；复杂时序或分支可用 Given／When／Then，按需引用 `R-xx`、`F-xx` 与操作标识。基础机制验收自身内循环与状态边界，组合与桥梁 Spec 验收新增互动与组合约束。
