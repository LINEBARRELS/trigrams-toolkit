# 编程功能开发与修复

## 适用与输入

明确开发目标、验收标准、执行边界、项目现状及关键依据。关键资料缺失或功能前置依赖未确定时及时反馈设计问题。

## 必要工作流程

规划期按本次工作阶段与决策点，通过 `handbook list --kind principle` 从对应 scope 选取所需条件原则，并将适用 principle ID 直接写入 Plan 的 `## 正式依据` 与 `## 验收标准`：
- **架构与框架设计阶段：** 必读 `programming-design-architecture` 下的全部原则；将 `programming-design-abstraction` 作为关键选读，按最小权威状态与派生计算、状态所有权、组合与继承建模、错误契约等决策点选取；涉及模块边界、仓库结构或实用取舍判断时，从 `programming-design-module`、`programming-design-repo`、`programming-pragmatic` 中按触发情境选取对应原则。
- **框架安装评审阶段：** 审核者验收框架契约产出时，必读 `programming-review` 下的全部原则，排查隐式耦合、不必要耦合与冗余中间层。
- **规模上限核对：** 审查或核对参数量、源文件行数、函数有效行与嵌套深度上限时，加载 `core:principle:programming-scale/keep-code-within-scale-limits`。
- **特定语言规范：** 声明类型与公开签名，或编写、修改、重构特定语言逻辑时，从涉及语言的 scope（`programming-csharp`、`programming-python`、`programming-typescript-javascript`）中选取对应的声明期或实现期原则。

<schedule-rule>
派发开发与审核 subagent 时，按本次工作类型参考以下方向与验收重点组织指导提示词：

| 工作 | 方法与验收重点 |
| --- | --- |
| 功能 | 沿入口、状态与消费者核对设计，复用既有能力；明确新增行为、失败语义及兼容要求，再实现可观察结果 |
| 修复 | 用最小代表场景复现期望与实际的差异，定位原因；修复后重验原场景、相关边界与消费者 |
| 重构 | 明确应保留的行为、公开契约及当前验证依据；按独立可验证范围改结构，持续核对行为与兼容性 |
</schedule-rule>

<exec-rule>
先核对并复用既有框架，补齐类、函数签名、类型、常量、枚举与核心工具定义，再填充逻辑与算法，重验目标行为及受影响消费者。完成后检查并清除代码中已失效的待办注释。
模块内有沉淀价值的局部经验时，可在模块代码所在目录用 `KNOWLEDGE.md` 记录简短、内聚的非强制指导与建议，正文仅限解释该模块内的思路和经验，禁止与模块外代码产生关联。
</exec-rule>

<exec-rule if="采用两阶段交接">
安装阶段仅交付源码框架、公共契约与安装验证，按必读原则标记源码并写明装填约束，不提前混入业务逻辑实现；待架构审核通过后再于装填阶段填充完整逻辑。
</exec-rule>

## 工序切分与交接

按可独立验证的行为范围划定 Stub，并按复杂度决定推进模式：
- **两阶段交接**：适用于跨模块契约、整体框架搭建或复杂接口定义；
- **单阶段完成**：适用于小型缺陷修复、局部重构或无跨模块新契约的简单改动（沿用默认单阶段流程，无需附加阶段门禁）。

<schedule-rule if="采用两阶段交接">
对适用 Stub 采用“框架安装 → 架构审核 → 逻辑装填 → 行为审核”两阶段推进：
1. 安装阶段完成后先派发架构审核；
2. 架构审核 `pass` 后，再派发逻辑装填阶段及行为审核；
3. 需要消费完整行为的后续 Stub 须等待上游装填阶段审核 `pass`。
</schedule-rule>

### 编程 Stub 两阶段交接对象

采用两阶段交接时，按架构安装与逻辑装填之间的框架契约定义 Stub。一个 Stub 可覆盖共同服务于该契约的类、函数和数据声明。常见交接对象如下，按本次需求选用：

| 交接对象 | 安装阶段确定的内容 | 装填阶段完成的内容 |
| --- | --- | --- |
| 服务或模块接口 | 职责、公开签名、输入输出与失败语义 | 业务逻辑、边界处理与消费者调用行为 |
| 数据格式与转换边界 | 字段、类型、约束及解析或转换入口 | 解析、校验、转换与真实数据处理 |
| 扩展点或处理流程 | 扩展接口、生命周期、调用顺序与依赖 | 调度、具体处理与组合行为 |

## 产出与验收

<review-rule if="采用两阶段交接">
**架构审核（框架安装阶段）：** 使用 principles 读取 `programming-review` scope 下的全部原则，严格审查框架设计是否存在隐式变更耦合（如派生状态冗余存储与多真相源同步、隐式全局状态、未声明的调用时序约定）、不必要耦合（如反向依赖、泄漏内部结构、调用方特判参数污染）与无独立变化理由的冗余包装或假扩展点；核对声明与约定一致、源码标识和交接注释可定位，并按承载形式通过编译、导入、类型检查或最小消费者接入确认骨架可引用。安装通过仅证明结构与契约可用，不替代完整程序验收。

**行为审核（逻辑装填阶段）：** 核对代码功能是否符合设计契约与验收标准，检查可观察行为、边界场景、消费者调用及失效待办注释是否已清除；确认汇报的实际修改、运行结果与证据一致，并列明未运行范围与原因。
</review-rule>
<review-rule else>
**单阶段综合审核：** 同时核对结构质量（无隐式变更耦合、不必要耦合或冗余中间层）与完整程序行为（符合设计契约与验收标准，边界场景与消费者调用通过验证，已清除失效待办注释）；确认实际修改、运行结果与证据一致，并列明未运行范围与原因。
</review-rule>
