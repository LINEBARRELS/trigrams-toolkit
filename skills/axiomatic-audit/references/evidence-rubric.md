# 证据判定与解耦手册

本手册为 `axiomatic-audit` 的独立取证标准，不依赖外部原则库。

## 1. 入口解析规则

- **`PRODUCT.md`**：仅提取程序的核心功能目标、主要用户场景与关键业务变化轴，用来校验模块或功能是否对应真实需求。
- **`docs/ARD.md`**：仅解析结构树：
  - `## <架构层名称>` → 架构层节点；
  - `### <arch-module>（Arch）` → 框架底座模块（标记 `role: "arch"`）；
  - `### <module-name>` → 业务模块（标记 `role: "business"`）；
  - `- **<feature-name>**` → 模块内正交功能点。
- **回避范围**：不读取 `DEVTECH.md`、`docs/implementation-specs/`、`docs/research/`、`docs/knowledge/`、历史 Plan 及源码注释里的设计意图叙述。所有依赖关系只以实际代码为准。
- **无 ARD 降级**：目标项目没有 ARD 时，结合 `PRODUCT.md`（或 `README.md` 简介）与源码顶层目录、启动入口反推 4 到 10 条顶层 FR，再映射到源码顶层包或目录作为 DP。

## 2. 两类依赖叉的判定标准

矩阵中的每条边都应附具体 `path:line` 源码证据。同一对 `(FR, DP)` 同时存在显式依赖和隐式变更耦合时，分别记录两条边（脚本会自动合并为 `D+C`）。

| 标记 | 名称 | 源码判定标准 | 典型证据形式 |
| --- | --- | --- | --- |
| `D` | 显式代码依赖 | FR 对应的源码显式 import、调用、继承或读写另一 DP 的公开或内部符号 | `import` 语句、直接函数/类调用、跨模块类型字段引用 |
| `C` | 隐式变更耦合（暗叉） | 虽无直接 import，但修改同一业务规则、状态或契约时，两处源码必须同步改动才能保持正确 | 跨模块平行 `switch`/枚举映射、双真相源手工同步、共享可变全局态/单例/暗通道文件、未显式约束的调用时序 |

**注意：** 仅依赖语言标准库或项目统一的基础设施原始类型（如通用数学向量、日志接口），不计入跨业务模块耦合边。

## 3. 三类架构失真与信息公理检查

1. **幻影节点（`phantom`）**：ARD 声明了该层、模块或功能，但源码中找不到对应实现，或仅存在空壳占位。写入 `frs` 时标记 `"status": "phantom"`。
2. **野生节点（`wild`）**：源码中存在承担实质业务职责的模块、目录或隐藏功能，但 ARD 未登记。写入 `dps` 时标记 `"status": "wild"`；如果它被活跃 FR 依赖或形成暗叉，照常记录边。
3. **框架底座（`Arch`）专项核查**：
   - 组合根（启动与依赖装配）允许单向引用各业务模块入口，正常情况下位于下三角矩阵的最底行与最右列。
   - 如果业务模块反向依赖组合根，或 `Arch` 模块内直接混入业务判断分支，应如实记录依赖边，让求解器暴露耦合环。
4. **信息公理（Axiom 2）信号**：
   - 在满足独立公理的前提下，排查纯透传包装层、单实现假接口、无独立职责的冗余列（`|DP| > |FR|`）以及必须按固定顺序手动调用多步接口的浅模块。

## 4. `matrix_solver.py` 输入 JSON 契约

```json
{
  "scope": "module",
  "title": "Module Level Axiomatic Audit",
  "mode": "paired",
  "frs": [
    {"id": "FR1", "name": "核心领域规则", "ard_ref": "docs/ARD.md#L18", "status": "present"},
    {"id": "FR2", "name": "外部命令编排", "ard_ref": "docs/ARD.md#L30", "status": "present"}
  ],
  "dps": [
    {"id": "DP1", "name": "src/domain/", "paths": ["src/domain"], "role": "business", "status": "present"},
    {"id": "DP2", "name": "src/app/", "paths": ["src/app"], "role": "business", "status": "present"}
  ],
  "pairs": [
    {"fr": "FR1", "dp": "DP1"},
    {"fr": "FR2", "dp": "DP2"}
  ],
  "edges": [
    {"fr": "FR2", "dp": "DP1", "kind": "D", "evidence": "src/app/runner.py:24", "note": "调用领域计算入口"},
    {"fr": "FR1", "dp": "DP2", "kind": "C", "evidence": "src/domain/types.py:11 <-> src/app/cli.py:88", "note": "平行维护同一状态枚举映射"}
  ]
}
```

- `scope`：取 `layer`、`module`、`feature` 或 `ad-hoc`。
- `mode`：架构层与模块层用 `paired`（固定 FR 与 DP 归属关系，防止重排掩盖逆向依赖）；功能层用 `bipartite`（允许矩形阵，并自动校验公理设计定理一 `|DP| < |FR|` 与 Hall 瓶颈）。
- `edges`：在 `paired` 模式下不必手写对角线自身边（脚本自动标记对角线 `●`），只需记录跨节点边；在 `bipartite` 模式下应记录全部 `FR → DP` 影响边。

## 5. 破环与解耦手法速查

针对求解器检出的问题类型，按下列方向提出具体、指向源码文件的重构建议：

| 检出问题 | 常见根因 | 推荐解耦手法 |
| --- | --- | --- |
| 显式耦合环（`D` 构成 SCC） | 双向 import，或上层与底层互持具体类型 | 在稳定侧声明抽象接口实现依赖倒置，或将双方共用的核心类型抽为独立下层模块 |
| 隐式升级耦合（仅 `D` 解耦，`D+C` 成环） | 平行规则表、共享可变状态或隐式时序约定 | 收拢规则常量、校验与计算到单一真相源模块；用显式参数与返回值取代共享可变态 |
| 功能层伪正交（Hall 瓶颈或 `|DP| < |FR|`） | 多个 ARD 功能挤在同一个可变状态对象或巨型分支内 | 按独立行为轴拆出正交状态与处理单元，或承认职责不可分并修订 ARD 边界 |
| `Arch` 底座耦合环 | 框架底座同时承载通用契约与启动装配，或混入业务逻辑 | 将底层稳定契约与顶层组合根拆离，并把业务判断移回业务模块 |
| 信息量过高（Axiom 2） | 无实质不变式的透传层或过多无主冗余 DP | 折叠纯转发包装，把内部格式与调用顺序收拢到深模块内部 |
