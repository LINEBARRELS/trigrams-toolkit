# delivery-review

进行独立审查，交付结论；不更新 Task 或 Plan 状态，不执行正式成果登记或 Plan 快照同步命令。Task 的 `result.md` 仅作为上次执行者的工作报告，不能替代真实证据。

## 审核范围与职责

按审核目标分为两类交付审核，分别对应局部核验与全局终验：

### 1. Task 交付审核（局部核验）
- **原则加载**：开始审核前，若 Task 存在“相关 principle”章节或验收标准指定了必读 principle，使用对应 ID 执行 `handbook load <ID> [<ID> ...]` 加载并阅读原则正文；已读且仍适用的内容不必重读。
- **核对重点**：对照 Task 验收标准、关联 Stub 阶段要求与已加载的 principle 正文，核对负责范围、公开契约、架构耦合与状态边界、下游交接及目录清洁度（无散落调试文件，探针均在根 `.tmp/`）。
- **证据核验**：必要时重跑关键测试，优先复用已有检查；检查产物已到达下游可读取位置。
- **输出位置**：保存为 Task 目录下的 `review.md`。

### 2. Plan 交付审核（总体终验）
- **核对重点**：读取 `summary.md`，对照总体目标、总体验收判据及整体交付范围，核对所有 Task 产物的整合结果与最终一致性。
- **证据核验**：验证跨 Task 组合行为与总体约束，清点遗留问题，确认无悬挂未决项。
- **输出位置**：保存为 Plan 根目录下的 `review.md`。

## 裁决判据

- **`pass`**：满足全部交付约定、验收标准及目录清洁要求。
- **`rework`**：产物不符合约定、存在缺陷、缺少必要改动，或目录散落未清理的临时调试文件。
- **`inconclusive`**：审核所需输入、方法或验证环境缺失，导致无法形成确切判断（需说明缺项与受影响范围）。

## 交付格式模板（review.md）

Task 与 Plan 审核统一采用两段式极简结构，严禁添加额外章节或散漫叙事：

```markdown
# [Txx 审核 | <Plan名> 总体验收]

## 审核结论

结论：`pass` | `rework` | `inconclusive`。审核日期：YYYY 年 MM 月 DD 日。
[宏观审核结论，字数严格限制在 100 字以内。直截了当给出判定理由，严禁罗列审核过程、读取文件列表、工作范围或背景交代。]

## 问题清单

### R01 [简要问题名称]
- **状态**：`open` | `resolved`
- **位置**：`path/to/file:line`
- **要求**：任务标准、契约或 principle 的明确要求
- **证据与影响**：实际代码/回执证据，说明为何不合规以及导致的阻碍或影响
- **最新动态**：（初审可留空；返工再审时在此追加最新核验结果）
```

## 审核与再审规则

1. **结论字数与范围限制**：`## 审核结论` 必须以 `结论：<pass|rework|inconclusive>` 开头。描述内容严格限制在 100 字以内，直言宏观依据，严禁流水账式罗列操作过程、阅读清单或工作范围。
2. **完全通过简洁性**：结论为 `pass` 且无问题时，`## 问题清单` 章节仅写单行 `无。`，严禁添加冗余描述。
3. **问题原子化**：所有阻碍项、缺陷或未决项，均以 `### R[编号] [问题名称]` 为章节拆分，编号按 `R01`、`R02` 顺序递增。
4. **返工再审原地更新**：
   - 返工后的再次审核严禁清空历史重写。
   - 必须在原 `review.md` 基础上更新：更新首行结论，在对应 `R[编号]` 章节内更新状态（如置为 `resolved`）并追加“最新动态”；
   - 若返工引入新问题，在末尾顺延递增编号（如 `### R03 ...`）；已解决的问题章节予以保留，供审计追溯。
