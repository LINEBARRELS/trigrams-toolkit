# why

追溯设计选择与关键变更，解释当时的目标、约束和取舍，并判断这些理由当前是否仍适用。本入口执行只读历史分析。

## 寻找证据

以用户指定材料、当前文稿、Git 和源码为主。无指定入口时，从 `docs/knowledge/decisions/` 与 `docs/knowledge/retrospectives/` 查起；核对当前代码设计时参考 `docs/implementation-specs/`。

用对象名称、旧称、路径、特征内容或关联编号建立线索，追到选择最初引入或变化的节点，读取关联讨论与前后版本。涉及 Git 时，检查改名历史、引入提交、同期修改和关联评审。

项目有专门取证流程或需补充方法时，按需调用 `workbook`，只采用所选 workbook 中的只读取证片段。保留资料所属项目、版本或时间范围；涉及源码包时区分维护源与安装副本。

仅在问题涉及登记身份、关系或 Plan 进度时，按需用 `project-state` 或 `plan-toolkit` 只读查询。查询失败，或遇到缺少身份、快照缺失、快照过期时，不自行补写或同步，将其记录为取证缺口（写明对象、结果与受影响的结论）。

## 分析方法

1. 明确待解释的选择与时间范围，将输入中提出的原因作为候选解释一并核实。
2. 重建当时面对的问题、目标和约束，区分记录中的备选方案与当前分析提出的替代方案。
3. 历史动机以当时记录为准；无直接记录时结合证据写明推导关系，无依据部分归入未知。
4. 比较支持与反驳证据。记录冲突时核对时间、对象和适用条件，无法消解时保留竞争解释。
5. 对照当前要求与实际成果，判断哪些历史约束继续有效、哪些已变化，以及对当前选择的影响。

围绕影响结论的缺口查证，证据足以回答问题时收敛。

## 组织调查

问题较广时，宜委派子代理承担历史搜索与分析以隔离上下文，传入待解释的选择、项目与时间范围、已有证据和材料入口；主 Agent 汇总并核对分歧，保留证据原有的确定程度。材料少、问题窄时直接在主线程完成。

## 给出结论

按已记录原因、合理推断、竞争解释与未知项依次作答，并说明已查范围与当前适用性。附上来源位置：Git 证据保留提交 SHA，Plan 关联使用实际目录，仅有历史标签时注明标签与来源。工具查询失败或状态缺失、过期时，单列取证缺口并说明受影响的结论。涉及后续决策时，指出仍应保留的约束与可重新考虑的选择。
