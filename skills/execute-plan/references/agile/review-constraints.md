# Agile 审核 subagent 约束

本文件约束 Agile 模式下承担 Stub 审核或 Plan 总体终验的独立 subagent。

## 审核准备与职责

1. **先读 Plan 与 `<review-rule>`**：审核前阅读 `summary.md`，聚焦本次审核对象的范围、验收标准、`<review-rule>` 与补充约束。
2. **独立取证**：以真实代码、产物、运行回执与验收标准为裁决依据；`Sxx-result.md` 的交付区仅作上次执行者的工作报告，不能替代真实证据。不修改业务代码，不更新 `summary.md` 状态头。
3. **加载 principle**：审核前使用 `handbook load <ID> [<ID> ...]` 加载 `summary.md` 中适用于本次审核的 `principle` ID（已读且仍适用的内容不必重读）。核查中发现改动涉及未覆盖的语言规范、架构耦合或边界风险时，自主使用 `handbook list --kind principle` 与 `handbook load` 检索并加载适用原则。

## 两类审核的核对重点

- **Stub 审核**（写入 `<Plan目录>/<StubID>-result.md` 末尾）：仅针对当前 Stub 与当前审核轮次，核对是否严守范围边界、满足本 Stub 契约与 `<review-rule>`、遵守适用 `principle`、自验真实充分及目录清洁（无散落调试文件，探针均在项目根 `.tmp/`）；必要时独立重跑关键校验。Stub 审核不代替 Plan 总体终验。
- **Plan 总体终验**（写入 `<Plan目录>/review.md`）：面向整个 Plan 的最终交付，对照 `summary.md` 的工作内容、总体验收标准与补充约束，核实 Plan 总体目标完成度、所有 `Sxx-result.md` 无未闭环的 `open` 问题并且目录清洁。

## 裁决判据

- **`pass`**：满足全部交付约定、验收标准及目录清洁要求。
- **`rework`**：产物不符合约定、存在缺陷、缺少必要改动，或目录散落未清理的临时调试文件。
- **`inconclusive`**：审核所需输入、方法或验证环境缺失，导致无法形成确切判断（应写明缺项与受影响范围）。

## 写入格式与再审铁律

- **Stub 审核**：在 `<Plan目录>/<StubID>-result.md` 末尾追加 `## 审核记录`（尚无该章节时新建；严禁改动上半区交付说明）。
- **Plan 总体终验**：在 `<Plan目录>/review.md` 中以 `# Plan 总体终验` 起头，随后使用同一套 `## 审核记录` 结构。

审核记录采用极简结构，严禁罗列阅读文件清单、审核过程流水账或背景复述：

```markdown
## 审核记录

- **[审核项] 结论**：`pass` | `rework` | `inconclusive`（YYYY-MM-DD）——[宏观判定理由，严格控制在 100 字以内，直截了当给出判断。]

### 问题清单

#### R01 [简要问题名称]
- **状态**：`open` | `resolved`
- **位置**：`path/to/file:line`
- **要求**：验收标准、契约或 principle 的明确要求
- **证据与影响**：实际代码或运行证据，说明不合规点及影响
- **最新动态**：（初审可留空；返工再审时追加最新核验结果）
```

1. **结论简洁**：每条结论理由严格限制在 100 字以内；无任何问题时，`### 问题清单` 下仅写单行 `无。`。
2. **问题原子化**：所有阻碍项、缺陷或未决项按 `R01`、`R02` 顺序编号拆分；同一文件内跨轮次新增问题顺延递增，不重号。
3. **返工再审严禁清空历史**：同轮次返工再审时，在原 `## 审核记录`（或 `review.md`）中更新对应结论行、在原 `Rxx` 下更新状态（如置为 `resolved`）并追加“最新动态”，已解决问题保留备查；同一 Stub 存在多个独立审核轮次时，在 `## 审核记录` 下按时间顺序追加新结论行。
