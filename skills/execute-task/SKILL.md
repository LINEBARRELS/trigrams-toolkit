# execute-task

## 接收与准备

读取 Task，了解工作目标、工作范围与交付产物。读取 Task 指定的输入与正式设计文档。

Task 声明 `installs`、`fills` 或 `uses` 时，读取 summary 中对应的 Stub 块。安装交付结构与交接约定，装填交付完整内容；`uses` 只保证安装阶段已验收。

开始工作前，若当前 Task 存在“相关 principle”章节，则使用该章节内的 principle ID，执行 `handbook load <ID> [<ID> ...]`，加载并阅读 principle 正文。已读且仍适用的内容不必重读。

## 执行与验证

完成 Task 工作范围内的工作，禁止越界。

不负责 Plan 和 Task 的状态变更、正式成果登记与快照同步；不修改非当前 Task 的历史 Plan、已完成 Task 或交付记录。

按验收标准选择必要验证，优先复用已有检查。交付约定或下游使用方式变化时，按实际影响确定验证范围并说明原因。

输入、方法或验收依据有缺项时，说明缺项、受影响部分及继续工作的条件或入口，继续不依赖缺项的工作。

## 交付

存在重要交付信息时，编写 Task 目录内的 `result.md`。按验收要求交付必要产出与验证。Task 目录的 `evidence/` 仅保存通过验收的最终关键证据。

调试探针、过程日志与中间临时数据一律保存在项目根目录的 `.tmp/`，不转储原始控制台日志或未提炼的数据至 Task 目录。

## 交付报告格式（`result.md`）

`result.md` 定位为面向审核者的**交付报告**与留档，真实产物本身即是成果证明，报告严禁撰写冗余长篇大论。各领域工作统一采用三段式极简结构：

```markdown
# Txx 交付

## 产物清单

- `path/to/artifact`：[新增 | 修改 | 删除] 核心交付内容简述。

## 验证依据

- [自验手段]：执行命令与退出码 / 规范核查比对 / 自动化回执，关键证据归档于 `evidence/`。

## 交接与遗留

- **调用/使用入口**：下游 Task 或使用方接手方式。
- **未决与限制**：本次未覆盖的边界或遗留问题（无特殊事项写“无。”）。
```

## 交付约束规则

1. **客观精炼原则**：
   - **不复述目标**：不复述 Task 目标、背景或任务描述。
   - **不写过程流水账**：不在报告中堆叠思考过程与试探步骤。
   - **不用主观修饰词**：不使用“完美、优雅、大幅提升”等主观修饰词，保持客观事实陈述。
2. **物先于言**：每一项改动必须以真实文件路径或具体产物为锚点，无实体产物变更不得空谈。
3. **凭据可溯**：自验依据必须指明具体手段与客观结果，仅将最终提炼的关键证据放入 `evidence/`，严禁口头无据保证。
4. **交接收敛**：若产物自解释且无特殊交接事项或遗留问题，`交接与遗留` 章节直接填写单行 `无。`。
