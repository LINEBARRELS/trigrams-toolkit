# Agile 模式规划指引

Agile 模式用于日常与中小型开发任务：以单份自包含的 `summary.md` 定义需求、依据、验收、约束与 Stub 清单，不拆分 `tasks/` 目录，不生成 `plan.json`，不使用 `plan-toolkit`。

## 目录与文件布局

沿用项目目录约定；无约定时使用 `docs/plans/<label>/`。

```text
docs/plans/<label>/
  summary.md      # Plan 唯一正文（含 YAML 状态头与全部 Stub 定义）
  S01-result.md   # 执行期由开发维护交付说明、审核追加结论（按 Stub 平铺）
  S02-result.md
  review.md       # 仅多 Stub 时的总体终验结论（单 Stub 时省略）
  evidence/       # 按需仅存放通过验收的最终关键证据
```

## `summary.md` 结构规范

`summary.md` 必须包含 YAML 头声明模式与当前状态：

```yaml
---
plan-type: agile
status: pending
---
```

`status` 取值范围为 `pending`、`doing`、`blocked`、`done`、`cancelled`。

正文按以下 5 个板块组织，使执行者与审核者仅凭 `summary.md` 与明确引用即可独立接手，执行与调度期不再回头查询 `workbook`：

| 板块 | 正文要求 |
| --- | --- |
| `## 需求目标` | 本次工作的核心目标、交付范围与明确的不做边界 |
| `## 正式依据` | 关联设计文档、Spec、公共契约与维护源的路径及章节链接；列出本次工作必读及按阶段适用的完整 `principle` ID（含审核阶段需加载的原则） |
| `## 验收标准` | 整体验收的可观察判据、必要验证入口；涉及正式成果登记或特定业务工具时，写明必要命令、参数来源与返回值处理 |
| `## 细节约束` | 接口契约、兼容边界、目录与编码约束、先后顺序以及本次工作特有的执行与审核规则 |
| `## Stub 清单` | 用 `### S01 <名称>`、`### S02 <名称>` 划定工作范围边界或关键交付单元 |

## Stub 编写要求

`Stub` 是 Plan 内通用的工作范围边界或关键交付单元（不限定于编程骨架）。编号为 `S` 加两位数字（如 `S01`、`S02`），在 Plan 内唯一。规模很小的单一改动可只设 `S01` 一项。

每个 Stub 块应写清以下信息：

- **负责范围与产物位置**：本 Stub 的具体交付内容、目标文件路径或交接位置。
- **前置依赖（按需）**：若依赖其他 Stub 的完整结果，或存在共享文件写竞争，显式指明执行顺序。
- **补充 principle（按需）**：若本 Stub 存在额外的领域或语言原则，列出完整 `principle` ID。
- **验收与审核节奏**：
  - 调度者默认在一个 Stub 完成后派发一次独立审核；
  - 若所选 `workbook`（如编程开发）要求某 Stub 采用多阶段审核（例如先安装框架契约并完成架构审核，再装填实现逻辑并完成装填审核），应在本 Stub 块内显式写明各检查点、阶段验收判据及对应必读审核 `principle` ID（如 `programming-review` 下的原则）。

未受正式依据或真实依赖约束的实现细节，交由执行者自主选择，不在 `summary.md` 中过度规定。

## 规划自检与修订

文稿完成后执行规划自检（不调用 `plan-toolkit`）：

1. **自包含且精炼**：核对所选 `workbook` 的必要工序、约束与原则 ID 已落盘到 `summary.md`，执行期无需再查 `workbook`；删除大段复抄、跨 Skill 通用规则或瞬时工作区状态。
2. **验证有效且必要**：每项交付要求与关键失败风险均有可区分合格与不合格的验证方式；Stub 依赖无环且无共享写冲突遗漏。
3. **引用可达**：核对 `summary.md` 中引用的本地文件路径、章节定位与 Artifact ID 真实有效。

修订进行中的 Agile Plan 时，核对已有进展与 `Sxx-result.md`，保留有效产物与已确认的历史审核结论；若修订影响已通过审核的 Stub，在 `summary.md` 中写明需重验的范围。

交付时向用户汇报 Plan 目录、自检结论、规划期发现的工作区状态与未解决缺项。
