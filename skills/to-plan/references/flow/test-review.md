# 验证编排审核（Flow 模式）

在计划交付前，检查 Task 的交接与验证安排，结论用于修订计划。本检查不执行 Task，也不替代执行后的验收。

## 获取分析数据

复用本次已通过且仍有效的校验结果；需重新校验时，按[定义与状态](format.md#定义与状态)处理。

运行 `plan-toolkit inspect <Plan目录>`，确认调用成功。从 `data.directory` 与 `data.tasks` 的 Task ID 定位 `tasks/<Task编号>/task.md`，读取声明和正文，并读取 summary 及关联 Stub 块。

对本次交付或修订中带 `specs` 的 Task，运行 `plan-toolkit inspect <Plan目录> <Task编号>`，逐项核对 `data.specs[]` 的 `path` 或 `error`。外层 `ok: true` 不代表全部 Spec 已定位。

命令失败或输入缺失时，报告问题、位置与影响范围。受影响部分暂不通过，继续审核可独立判断的部分。

## 审核方法

以所选 workbook、正式依据、已有产物与验证证据核对计划正文。

1. **交接是否充分且精炼。** 按[summary 的结构与依据](format.md#summary-的结构与依据)与[Task 的内容结构](format.md#task-的内容结构)核对 workbook 的必要要求是否落实，确认适用 principle 已准确分发至对应 Task 的“相关 principle”章节。判断执行者凭 Task、关联 Stub、明确引用与输入能否完成工作并判定结果。强制步骤应有正式依据或真实依赖，必要流程的条件与分支应明确；依赖或 Task 边界妨碍执行时一并指出。文稿若大段复抄既有决策或协议正文、复述跨 Skill 通用运行规则，或混入规划期瞬时工作区状态与规划自检记录，应要求删减。
2. **验证是否有效。** 每项交付要求和关键失败风险应有验证方法与负责的 Task。方法应能区分合格与不合格结果，写清输入、预期结果与证据。整体审核依据应能从 summary 及其明确引用取得。Stub 可随所属成果或下游使用场景验收，不必单设检查入口。
3. **验证是否必要。** 对每组验证，判断去掉后会失去哪项必要证据；已有验证足够时复用或合并。按证据价值判断，不按数量或方法类别判断。
4. **范围是否合适。** 结合项目要求、交接约定、下游用途与共享产物，核对本次检查及交付前的整体验证范围。存在条件性扩展时，写明触发条件。Task 开工依赖不能代替产物影响关系。

## 返回结论

直接返回“通过”或“需修改”，不创建审核文件。

- 每个阻碍验收的问题写明位置（summary / Task / 验证项）、要求或产物依据、缺失或冗余内容，以及修改理由。
- 可选改进与阻碍问题分开列出。
- 计划修订后，重新获取受影响的分析数据，复核原问题与受影响部分。无未解决的阻碍问题时，通过审核。
