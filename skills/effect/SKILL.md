# effect

评估变更如何影响成果、实际使用方和在途工作，找出触发条件与需验证的关键前提。本入口执行只读分析。

## 寻找证据

以用户指定材料、当前文稿、Git 和源码为主。从变更前后内容、目标路径或 ID 和已知使用方出发，沿项目导航追查关联材料。无项目约定时，设计从 `docs/implementation-specs/` 查起，历史依据从 `docs/knowledge/decisions/` 与 `docs/knowledge/retrospectives/` 查起。

仅在问题涉及登记身份、关系或 Plan 进度时，按需用 `project-state` 或 `plan-toolkit` 只读查询；涉及 workbook 或 principle 变更时，按需用 `handbook` 查询正文，并按输入采用指定的项目资料或源码包。查询失败，或遇到缺少身份、快照缺失、快照过期时，不自行补写或同步，将其记录为取证缺口（写明对象、结果与受影响的结论）。

在 Registry 已登记关系之外，继续从文稿、Task、资产和操作约定搜索实际使用方式；存在代码调用方时，追踪调用链、配置、数据格式与生命周期。名称或符号未命中时，检查读取产物、依赖旧行为或执行后续步骤的对象。

## 分析方法

1. 说明变更前后发生变化的语义、承诺或适用条件，包含差异文本未直接写出的隐含变化。
2. 找到依赖原有承诺的使用方，按实际使用方式追踪变化如何传播到下游结果。
3. 写明每项重要影响的触发条件、传播过程与可观察后果，结合当前版本、配置和使用方式判断路径是否可达。
4. 对照当前成果、约定和使用方重判历史风险；当前结构、工作过程或在途状态不明且影响结论时调用 `how`，缺少历史依据且影响结论时调用 `why`，传入具体问题与已有证据补查。
5. 找出判断依赖的关键前提，区分材料支持、路径推演与实际验证，并为未验证前提设计最小验证动作。

关键影响已有证据且剩余未知项明确后即可收敛。可引用已有验证结果；新增测试、复现或修订交给获授权的执行流程。

## 组织调查

问题较广时，宜委派子代理承担影响调查，传入变更前后内容、项目与版本范围、已知使用方及已有证据；主 Agent 合并重叠结果并回查分歧。材料少、问题窄时直接在主线程完成。

## 给出结论

先说明行为变化，再分开列出已确认影响、已排除风险与待验证项，按触发条件和后果安排优先级。每项重要影响写明受影响对象、触发条件、后果、证据和最小验证动作；已排除风险写明排除依据。工具查询失败或状态缺失、过期时，单列取证缺口，不填补未证实影响。涉及在途工作时，指出受影响的未完成 Task、需重验要求及实际 Plan 目录；已完成历史保留原记录，后续修复由新 Task 承接。
