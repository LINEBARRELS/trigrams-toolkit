# decision-maintenance

接收明确指定的决策主题、删改要求与当前对话上下文，维护项目决策目录及其索引 `index.md`（无项目约定时使用 `docs/knowledge/decisions/`）。

1. 从当前对话与明确输入中提炼已拍板的决策要素：问题与背景、约束前提、候选方案、最终选择、承受代价，以及关联的讨论来源、提交或 Plan 目录。
2. 检索项目决策目录中的同主题或关联 Plan 记录，按变更性质确定维护方式（动笔编辑文档前使用 `doc-polish`）：
   - **新增记录**：尚无同主题记录时，按主题（或关联 Plan 目录与主题）创建决策文件。
   - **勘误与清理**：纠正记录偏差、合并同主题碎片或清理明确指定作废的条目时，直接原地更新或删除对应文件。
   - **推翻与演进**：因约束变化或新结论推翻既有决策时，在同主题文件内更新现行结论，并折叠或附注原取舍及推翻原因，保留供 `why` 追溯的历史证据链。
3. 维护决策目录索引（`index.md`），便于快速检索并控制条目篇幅：
   - 每次新增、合并、推翻或清理决策文件后，同步更新项目决策目录下的 `index.md`。
   - **分类方式**：按实际宏观主题与业务场景划分为二级标题（如原则体系、架构解耦、工具契约、工程设施等），不设深层嵌套。
   - **条目内容量要求**：每条记录仅保留相对路径链接与 1 到 2 句话的简要说明，说明该决策的核心选择与解决的问题，严禁堆砌长篇背景或对比细节。
   - **状态附注**：条目若被归并或重定向，在简述末尾附注说明（如 `（已归并至 xxx.md）`），保留历史溯源入口。
4. 当对话包含多个未定分支或涉及既有记录删改，而指令尚未明确取舍边界时，先列出拟写入或删改的摘要供用户确认；指令已明确给出结论与操作范围时，直接更新决策文件与索引。
5. 仅写入或删改项目决策目录中的文件（决策文档与 `index.md`）。若本次决策同时改变现行架构契约（`DEVTECH`、`ARD`、`Implementation Spec`）或跨任务判断标准（`principles`），在交付决策文件路径与变更摘要后，单列受影响的文档或 principle 供用户定夺。
