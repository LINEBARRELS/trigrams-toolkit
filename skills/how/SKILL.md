# how

调查当前结构、工作过程、职责分工或在途状态，形成解释实际行为的机制说明。本入口执行只读调查。

## 寻找证据

以用户指定材料、当前文稿、Git 和源码为主。无指定入口时，从 `DEVTECH.md`、`docs/ARD.md` 和 `docs/implementation-specs/` 查起，再追到实际产物、配置和验证记录。

用名称、职责、路径或 ID 定位对象；名称未命中时，改用旧称、输入输出或可观察行为查找。沿引用和实际使用方式扩展，只读取回答当前问题所需的材料。

仅在问题涉及登记身份、关系或 Plan 进度时，按需用 `project-state` 或 `plan-toolkit` 只读查询。查询失败，或遇到缺少身份、快照缺失、快照过期时，不自行补写或同步，将其记录为取证缺口（写明对象、结果与受影响的结论）。

## 分析方法

1. 明确待理解的行为、责任边界或状态。小问题追一条主线；跨组件问题按职责或流程阶段拆开。
2. 从触发场景追到可观察结果，说明每一步的负责方、输入输出，以及数据和状态变化。
3. 检查改变结果的关键分支、边界与失败路径；依据契约、依赖方向和实际使用判断职责归属。
4. 对照正式设计、实际产物和验证证据，区分设计意图、当前行为与执行进度；出现分歧时回查对应材料。

关键过程能够连贯解释，且影响结论的分歧已核实后即可收敛。当前判断需要历史原因时，按缺口调用 `why`，传入具体问题与已有证据。

## 组织调查

问题较广时，宜委派子代理承担搜索与分析，传入具体问题、项目与版本范围、已有证据和材料入口；主 Agent 汇总并回查关键分歧。材料少、问题窄时直接在主线程完成。

## 给出结论

先概括机制，再说明关键过程与责任边界，使读者能据此判断系统行为。附上继续查证所需的文件、章节、符号或实际 Plan 目录。工具查询失败或状态缺失、过期时，单列取证缺口并说明限制了哪个判断。仅在任务要求时保存报告。
